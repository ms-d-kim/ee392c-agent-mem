## 2. Differentiated-memory insights drawn from the data

These are the load-bearing observations for the DMS argument, each grounded in a
committed number and kept strictly within the logical/analytical boundary.

1. **Capacity-time and access-frequency are orthogonal — this is the core DMS
   motivation.** Aggregated over the full 20-trace v2 batch
   (`fig3_capacity_vs_logical_reads`), analytical KV holds ~99.99% of
   byte-seconds but only ~3.5% of logical read events; prompt/tool/assistant
   objects invert that ratio (negligible capacity, ~96% of reads). A placement
   policy keyed on access frequency alone would strand KV in a hot tier; one
   keyed on capacity alone would evict hot scaffolding. You need *both* axes,
   which is precisely the case for ≥2 differentiated tiers with different
   objective functions (latency/bandwidth-optimized vs capacity-optimized).

2. **The benefit of a "resident reuse" tier is workload-structure-dependent, and
   semantic memory ops can erode it.** Prefix caching cuts cache-adjusted new KV
   by 84.3% in the coding replay (long stable shared prefix). But in the
   compaction replay, turning compaction *on* lowers the cached fraction
   (0.783 → 0.536) and *raises* new-prefill tokens (4,826 → 5,740) even while it
   cuts retained raw-context KV from 1.03 GB to 443 MB — because inserting a
   summary breaks prefix-cache contiguity. The honest systems statement is a
   tradeoff ("compaction trades retained capacity for prefix-cache disruption /
   recompute"), not "compaction makes inference cheaper."

3. **There is no fixed "Tier-3" object type; the capacity sink is set by workload
   shape.** Logical projected KV is dominated by compaction `raw_context`
   (443 MB on / 1.03 GB off), then `assistant_history` (51–223 MB depending on
   workload), then search `search_result` (23 MB), with all prompt scaffolding
   under ~1 MB. The natural target for a large/cheap tier is whatever class the
   workflow accumulates — retained context, chat history, or retrieval results.
   This argues for a *semantic-class-aware, per-workload* demotion policy rather
   than a static object-type → tier table.

4. **Cost is set by what is admitted to context, not by what is scanned.** Both
   search traces scan the identical 88,372 B corpus, yet broad retrieval
   returns/inserts 2–3× more and carries 3.22× the `search_result` logical KV.
   Scan volume (transient, read-only) and resident KV pressure (what enters
   prompt history) are decoupled — motivating a cheap scratch/streaming tier for
   scan buffers, distinct from the resident KV tier.

5. **Cross-representation amplification is large but irreducible in KV.**
   Text/token duplication factors are ~1.7–2.3× per class; KV-vs-text
   amplification is ~8,000–20,000× (the 56 KiB/token GQA projection). Logical-level
   dedup could trim text/token redundancy, but the dominant byte-seconds cost is
   intrinsic to the KV representation — so the capacity tier's job is managing KV
   lifetime, not deduplicating text.

Together these support the three-tier prescription in `fig4_dms_tier_proposal`
without overreaching: stable repeated prefixes → low-latency resident reuse;
active KV + recent context → bandwidth-sensitive; bulky lower-reuse retained
context → capacity-oriented and the natural demotion target.

## 3. Improvements applied in this pass

All changes are in-scope (no schema change, no new measurement, no scope creep)
and preserve the experiment's purpose. Each was verified.

1. **`analysis/plots.py` — fig3 now aggregates the full v2 batch.**
   `fig3_dichotomy` globbed only `hello_bug*.jsonl` (10 of 20 traces) while its
   caption and `figures/README.md` describe it as "across historical v2 traces"
   (fig1/5/6/7 already use all 20). Changed the glob to `*.jsonl` and regenerated
   `figures/fig3_capacity_vs_logical_reads.{png,svg}`. The dichotomy is robust:
   KV stays at ~100% of byte-seconds and moves from 3.34% → 3.46% of read events.
   This closes the last open item (#5) from `reviews/03`.

2. **`validation/validate_final_v3.py` — the cached-token gate is no longer
   vacuous.** Added `validate_cross_check_coverage`: a trace must carry an
   `engine_cross_check` event on every prompt-construction step, anchored to the
   independently-emitted per-step KV prompt spans. Previously a truncated trace
   with zero cross-check events passed the AGENTS.md hard gate silently. Verified:
   all six real traces still PASS; a trace with cross-check events stripped now
   FAILs with a clear message.

3. **`README.md` — "Reuse count" definition sharpened.** Headline metric #2 now
   states that final-v3 `logical_read_events` counts representation-level
   prompt-construction accesses (a text read and a token read of the same object
   on the same step are two events; cached-prefix KV reuse contributes its own
   reads), and is a logical-access-intensity signal, not a deduplicated revisit
   count or a hardware transaction count. This removes the mismatch between the
   generic "accesses after creation" wording and what the column measures.

4. **`README.md` — final-v3 command path points to the one-real-trace gate.**
   Added a one-line pointer to the `SETUP.md` run order (synthetic gate + single
   real trace verifying cached-token extraction is not `unavailable`) before the
   `--all` six-trace sweep, reconciling the README summary with the SETUP runbook
   and AGENTS.md gate.

5. **`analysis/final_v3.py` + figure docs — `lifetime_reuse` now uses
   step-normalized lifetime.** DECISIONS §2 says step-count is the better
   cross-task comparison axis, but the final-v3 diagnostic scatter still used
   wall-clock seconds. Switched the x-axis to `lifetime_steps`, regenerated the
   figure, and updated the README/figure descriptions to make that convention
   explicit.

6. **`validation/assert_validate_final_v3.py` + docs/Makefile — validator
   regressions are now codified.** Added a small no-pytest regression script
   covering the failure modes the real six-trace sweep does not exercise:
   missing `engine_cross_check` coverage, dropped per-step coverage,
   `cached_tokens > prompt_token_count`, and `cross_check_status="unavailable"`.
   Wired it into `make verify-v3-validator` and inserted it into the documented
   final-v3 run order so the strengthened cached-token gate is itself checked,
   not just relied upon.

## 4. Tracked items deliberately left unchanged

These are real but either out-of-scope to "improve without deviating," historical
(v2) code, or stylistic. Listed so they are not lost, not because they block the
final-v3 artifact.

- **Dead/half-finished scaffolding:** `agent/graph.py`, `agent/tools.py`,
  `analysis/duplication.py` raise `NotImplementedError`, and
  `requirements.txt` still pins the unused langgraph/langchain/openai stack.
  Final-v3 is explicitly scripted and does not use them; removal is a cleanup
  decision for the authors, not a correctness fix.
- **`agent/run_vllm.py` (historical v2):** `read_file`/`write_file` join a
  model-supplied `path` under `task_dir` with no `..`/absolute guard. Harmless
  for the checked-in fixtures but a path-traversal footgun if the v2 harness is
  ever reused on untrusted output.
- **`agent/run_batch.py`** uses `time.time()` for a load-duration measurement,
  against the `time.monotonic()` style rule (AGENTS.md). Nit, historical path.
- **`search_corpus_scan`** is modeled as a live text object sized by total
  scanned bytes, so its byte-seconds treat a transient scan counter as resident
  memory. Defensible as a "scan pressure" proxy but worth a caption caveat if it
  ever appears in a headline figure (it currently does not).
- **`byte_seconds` per `semantic_type`** sums two lifetime conventions
  (text/token to task-end vs `kv_estimated` bounded at the next prefill). This is
  intentional per DECISIONS §2 but is a subtlety the report should state once.
